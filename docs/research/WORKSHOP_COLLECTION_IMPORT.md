# Native Workshop collection import (2026-10-25)

## Import recovery and load measurements (2026-10-25)

Source tracing found that Stop Import closed the review, worker status replaced collection context, cached-item progress was not reflected in the table, and unreadable metadata failures omitted item identities. The existing callback/worker/dialog flow now supplies those states without another downloader, persistence layer, or activation path. Cached duplicate-resolution results and unsaved profiles remain reusable. Invalid fetches clear old review state; an edited link disables import until fetched again. Available Mods, Active Order, and explicit load/review/apply retain their responsibilities.

Deployment previously hashed each entry, hashed it again before verified copying, recopied all owned folders even on a same-pack reload, and archived unchanged folders. It now passes the measured source digest to the existing copier, hashes a physical entry once per preparation, and retains ownership-recorded folders with unchanged digests. All prior deployed folders are fully verified immediately before activation, including retained ones; rollback leaves retained folders in place and restores replaced folders. A changed cache, modified local copy, link, unowned destination, or changed ownership snapshot still blocks unsafe activation.

Repeatable fixture: `.venv/Scripts/python.exe tests/benchmark_collection_load.py`, Windows/Python 3.14, 30 Workshop items, 64 distinct 8-KiB media files per item (1,920 files, 15 MiB plus metadata), three rounds. Setup/cache interning and user prompts are excluded. Sequential comparison used the `6817a7f` deployment implementation followed by the modified implementation, sharing the same hashing/copy implementation, on disposable folders. Median first load: **6.871 → 6.069 s**; same-pack reload: **7.915 → 2.718 s**; switch from all 30 to 15 retained items: **4.419 → 1.687 s**. Disk cache, antivirus, item size, and storage affect these timings. This does not establish live-library or game loading performance. Full cache and owned-file integrity reads remain a deliberate cost.

Native Windows Qt renders were inspected at 960×680 and 740×540, also with Qt scale factors 150% and 200%, for retry, unavailable/foreign, empty, long-name, and 2,000-item reviews. Shortened headers and flexible columns removed horizontal clipping at those sizes; full cell values remain in tooltips. The fixture [retry screenshot](../screenshots/collection-import-retry.png) records the changed layout. No Steam downloads, packaged workflow, or gameplay were exercised during this iteration.

## Faster collection loading research (2026-10-25)

The visible `Preparing collection mod folders: 48/166` counter iterates `sources`, keyed by each distinct mod-folder SHA-256 digest. It counts content folders, not bytes or elapsed work; one folder may contain far more files or data than another. The progress bar itself is indeterminate.

For a new local copy, the current path reads the same mod bytes repeatedly: `CollectionStore.scan()` verifies the full cached Workshop item; `prepare()` hashes each mod entry to derive its destination identity; the custom `copy_file` reads and writes the data; then `copy_verified_tree()` hashes both the source and staged destination again. On the source content this is roughly four full reads, plus one read of the staged copy and the write. A same-pack reload skips copying but still verifies the cached item, each mod entry, and the old deployed copy immediately before activation.

Repeat run of `tests/benchmark_collection_load.py` on the current code: Python 3.14.7, C: NTFS, 30 Workshop items, 1,920 distinct 8-KiB media files (15 MiB plus metadata), three rounds. Median first load was **8.172 s**, same-pack reload **3.487 s**, and a switch retaining 15 of 30 folders **2.194 s**. Setup/cache interning is excluded. These numbers are a current synthetic baseline, not a timing for the user's 166-folder pack and not a measurement of the proposed changes.

Two primary-source options look practical without new dependencies:

1. Fold the complete cached-item integrity walk and the per-mod-folder digest calculation into one traversal, feeding the same file chunks to the item and applicable folder hash contexts. Then copy each new folder into the existing private transaction staging area with a Windows `CopyFile2` adapter, `COPY_FILE_FAIL_IF_EXISTS`, and a progress/cancel callback; hash the staged destination against the expected folder digest once. This keeps the exact-content check, no-overwrite behavior, cancellation, ownership journal, and rollback while removing redundant full reads. CPython v3.14.7's `shutil.copy2()` calls native `CopyFile2` on Windows, but this project supplies its own `copytree` file callback to enforce exclusive creation and chunk-level cancellation, so it bypasses that native path. A purpose-built wrapper must preserve those guarantees; replacing the callback with plain `copy2()` would not be sufficient. See [CPython v3.14.7 `shutil.py`](https://github.com/python/cpython/blob/v3.14.7/Lib/shutil.py#L2983-L3045), [Python 3.14 copy documentation](https://docs.python.org/3.14/library/shutil.html#shutil.copy2), and Microsoft's [CopyFile2 API](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-copyfile2) and [progress/cancel callback](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nc-winbase-pcopyfile2_progress_routine).
2. Where the cache and Zomboid mods directory are on the same ReFS volume, the Windows native copy path can additionally use block cloning on supported Windows 11 builds. ReFS makes the clone copy-on-write, so edits in one file do not alter the other; the feature is unavailable on NTFS and needs an ordinary-copy fallback. The current benchmark ran on NTFS, so it provides no evidence for this optional path. See Microsoft's [ReFS block-cloning behavior and limits](https://learn.microsoft.com/en-us/windows/win32/fileio/block-cloning).

Hard links are not suitable for the shared cache: Windows hard links are multiple names for one underlying file, so edits through the deployed mod path change the cached file too. That breaks pack isolation and later integrity checks. Microsoft's [hard-link documentation](https://learn.microsoft.com/en-us/windows/win32/fileio/hard-links-and-junctions) describes this shared-file behavior.

The UI still reports folder-count progress rather than byte-weighted progress or an estimated remaining time; that is a separate feedback improvement. The same-cache benchmark below has now validated the single-pass hashes, bounded concurrency, native copy, and archive-only unload. ReFS block cloning remains a follow-up only if an appropriate disposable ReFS volume is available; this benchmark ran on NTFS.

### User-supplied real collection and unload benchmark (2026-10-25)

The user supplied [Project Viewpoint Vanilla+](https://steamcommunity.com/sharedfiles/filedetails/?id=3812346398) as the reference workload. Steam currently lists 142 items; its page also says the collection was removed from the community and is incompatible. The app's read-only collection API still returned 142 Project Zomboid items with none unavailable or foreign. No new downloads or subscriptions were made. The local saved copy references 141 of those 142 Workshop IDs and contains 166 Mod IDs; all 141 referenced cache objects were present. This is therefore a close real-content benchmark, but not an exact match to today's page.

An isolated baseline run used the original Python 3.14.7 implementation, the existing local cache, and a temporary `Zomboid/mods` directory on C: NTFS. It measured **519.490 s** for first deployment, **193.319 s** for same-pack reload, and **44.312 s** to load an empty-content profile as an unload surrogate. First-deploy intervals were 97.27 s validating/scanning cache items, 66.67 s hashing mod entries, 355.25 s in the copy phase (including source/destination hashes and the final move/index commit, not raw-copy time), and 0.28 s scanning the temporary library. Reload spent 77.55 s validating/scanning cache items, 71.67 s hashing mod entries, and 43.86 s checking deployed folders. The unload surrogate spent 44.30 s hashing deployed folders. These are single-run timings, not medians, and exclude Steam downloads, dialogs, global-list apply, game startup, and gameplay.

The implementation combines each full-item digest with the contained mod-entry digests in one traversal. Independent item trees are verified in a bounded four-worker pool with deterministic result order. New copies use Windows `CopyFile2` with `COPY_FILE_FAIL_IF_EXISTS` and a progress/cancel callback, also capped at four workers across separate mod folders. Each staged destination is still hashed against its expected digest; the redundant source rehash is removed because the full cache item was verified before copying. Cancellation stops sibling jobs, and partial files stay inside the transaction's prepared directory. See [CPython v3.14.7 `shutil.py`](https://github.com/python/cpython/blob/v3.14.7/Lib/shutil.py#L2983-L3045), Microsoft's [CopyFile2 API](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-copyfile2), and its [progress/cancel callback](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nc-winbase-pcopyfile2_progress_routine).

The real pack contains 141 cached Workshop items and 166 Mod IDs, with about 2.80 GB across 80,072 files. On the same machine and disposable target, the final four-worker implementation took **195.956 s** for first deployment, **89.038 s** for same-pack reload, and **9.970 s** for unload, improvements of 62%, 54%, and 78% against the original single-run baseline. Cache-only verification measured 69.8 s sequential versus 36.5 s with four workers. A copy+verify sample of 10,000 files / 425 MB measured 31.9 s sequential, 19.7 s with two workers, 12.4 s with four, and 10.2 s with eight. Eight workers were only 1.8 s faster than four in the full pre-hash-parallel run, so the implementation keeps the four-worker cap. These are single local runs, not medians or guarantees for slower disks; the optimized first load still takes about three minutes here.

Unload now has an explicit **Unload Pack** action. Deployment-index schema 2 records device/file identity for each owned folder while schema 1 remains readable. When identity matches, unload uses a metadata-only walk to reject links and unusual file types, then moves the recorded folders into the transaction recovery archive without reading their contents. Any edits remain recoverable. Legacy records without IDs use an exact full-tree hash. Unload leaves global `default.txt` and the staged Active Order unchanged; reactivation still verifies exact content. The archive is retained and not automatically deleted. The moves stay within the same `Zomboid` directory and are same-volume renames ([MoveFile](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefile)).

Directly loading from the private cache through the game's existing `-modfolders` argument is not supported by the installed loader. Read-only `javap` inspection of the installed Project Zomboid jar (Steam app build ID `25485521`, 2026-10-25) confirmed that `MainScreenState` passes the following argument to `ZomboidFileSystem.setModFoldersOrder()`. That method splits on commas, and `getAllModFolders()` only recognizes the literal tokens `workshop`, `steam`, and `mods`, mapping them to the game's built-in roots; a cache path token is ignored. This rules out removing deployment copies through a launch argument without a game-side change. Junctions or symlinks would still conflict with the app's path/link safety rules.

An NTFS USN change-journal cache could theoretically avoid full rehashes between verified loads, but journal history can be trimmed or discontinuous, and Microsoft's identifier/query flow requires administrator privileges. Treat it as a later optional experiment with full-hash fallback, not a default shortcut ([change journals](https://learn.microsoft.com/en-us/windows/win32/fileio/change-journals), [journal identifier](https://learn.microsoft.com/en-us/windows/win32/fileio/using-the-change-journal-identifier)). Do not use modification timestamps alone as an integrity check.

ReFS block cloning remains a conditional option for first copies only when cache and destination are on the same ReFS volume and supported Windows copy operations are used. This benchmark volume is NTFS, so it cannot benefit. Hard links remain unsuitable because edits through either path change the same underlying file; directory links also conflict with the app's link rejection and directory ownership model ([ReFS block cloning](https://learn.microsoft.com/en-us/windows/win32/fileio/block-cloning), [hard links and junctions](https://learn.microsoft.com/en-us/windows/win32/fileio/hard-links-and-junctions)). Copying a prepared duplicate during import would shift the wait earlier and consume more disk; it would not reduce total copying unless a verified same-volume clone path is available.

## Current shared-cache design (supersedes the original subscription flow)

The user explicitly requested anonymous downloads, one global shared collections folder, exact-content reuse, and visibility only after a pack is loaded. They approved SteamCMD and isolated testing. The native browser remains; the subscription adapter and its tests were replaced with private download/deployment coverage.

- The official [SteamCMD bootstrap](https://steamcdn-a.akamaihd.net/client/installer/steamcmd.zip) was downloaded into an isolated temporary directory. Windows Authenticode verified Valve's bootstrap (`O=Valve`) and its updated executable (`O=Valve Corp.`). The adapter requires a valid signature from either exact publisher name and isolates updater child processes in a Windows job for cancellation.
- `+login anonymous +workshop_download_item 108600 2169435993 validate +quit` successfully downloaded a 31,729-byte public item without changing subscriptions. The adapter repeated this and verified Steam's receipt. Importing it twice produced one shared content object. SteamCMD's bootstrap returned exit code 1 despite successful child download, so success requires the exact item-success marker plus an installation receipt, not exit code alone. Restrictions are reported; no authentication or access bypass is attempted. [Valve issue documenting Workshop command behavior](https://github.com/ValveSoftware/steam-for-linux/issues/12339).
- Shared objects hash all relative paths, types, and file bytes. Packs use schema-v4 exact references; mismatching versions are separate. Loading prepares the pack's exact app-owned copies in `Zomboid/mods` and gives those entries priority for matching Mod IDs in the app's loaded-pack scan and preflight. Conflicting user/Steam copies stay untouched. Loading reuses the last Workshop scan and rescans local roots only, instead of traversing every Workshop item again. Prior app-owned copies are archived outside the scanned mod root.
- The game's documented local `Zomboid/mods/<entry>/` layout is used, retaining root/common/versioned metadata. A read-only inspection of the installed `projectzomboid.jar` found `ZomboidFileSystem.getAllModFolders()` defaults to `workshop,steam,mods`; `setModIdToDir()` uses `putIfAbsent`, so the first discovered matching Mod ID is kept. `MainScreenState` accepts `-modfolders` and passes its comma-separated value to `setModFoldersOrder()`. When a collection is loaded, ZomboidSorter includes `-modfolders mods,workshop,steam` in its Steam launch link so the app-managed local copy precedes Workshop copies for that launch. No persistent Steam Launch Options, subscriptions, or installed mod files are changed. This source inspection does not verify Steam's argument forwarding or a live game launch; duplicate local entries inside `Zomboid/mods` and gameplay remain unverified. [The Indie Stone's Build 42 layout explanation](https://projectzomboid.com/blog/news/2024/08/tidy-up-time/).
- The normal workspace is now **Available Mods / Active Order**. Cached unloaded collections never enter discovery; a loaded pack's disabled mods remain available to re-add. Literal ampersands in Qt tabs/buttons are escaped to prevent accidental shortcut underlines. Collection loading now selects the deployed collection copy when other installed entries share its Mod ID, while retaining those files on disk.
- Collection pack loading no longer scans configured Workshop roots. It refreshes local mod roots and carries forward the latest completed Workshop result. This avoids repeating the expensive 64-folder scan shown in the user's load dialog. Fixture checks cover priority selection and reuse of Workshop results. The installed game's loader source supports local-before-Workshop ordering, but Steam argument forwarding and game runtime remain unverified.
- Follow-up from user-reported slow imports and unclear revisit state: the importer reuses SteamCMD folders only when current installation receipts match fetched item metadata. New downloads use one session for up to 200 item commands, and exact success markers plus receipts are still required for each item. If SteamCMD exits or stalls after partial results, verified completed items are interned before the error is reported; cancellation and timeout leave partial SteamCMD files for retry. Reopening a collection review shows local installation, private receipt-verified downloads, and matching saved-pack content separately. Default collection names get a suffix when a different existing pack has the same title. This flow has not yet been exercised against a real multi-item collection or packaged app.

## Sources inspected

- [Steam public PZ collection catalog](https://steamcommunity.com/workshop/browse/?appid=108600&section=collections&browsesort=trend): the current HTML has a `valve-ssr-data` script. `renderContext.queryData` contains the `workshop_browse` query scoped to app `108600` and section `collections`. Results carry `file_type=2`, title, creator, summary, child count, favorites, updated timestamp, and tags. Creator names come from `PlayerLinkDetails` queries.
- [Current Steam browse UI source asset](https://cdn.fastly.steamstatic.com/steamcommunity/public/ssr/D_C_OT9u.js): collection sorts include `trend`, `toprated`, and `mostrecent`. `lastupdated` also returned collection results in the live read-only probe. The old `totaluniquefavorites` sort returned no results and was excluded.
- [Steam RemoteStorage API](https://partner.steamgames.com/doc/webapi/ISteamRemoteStorage): live published-file replies use `consumer_app_id`, not the old importer's expected `consumer_appid`. Child collection types are in `children[].filetype`; the observed published-file detail reply omits file type. Support both app-ID spellings and expand nested collections using child types with cycle/depth/item/request limits.
- [Steam subscription UI source](https://community.fastly.steamstatic.com/public/javascript/sharedfiles_functions_logged_in.js): `SubscribeCollectionItem` posts `id`, `appid`, `include_dependencies=false`, and in-page `g_sessionID` to `https://steamcommunity.com/sharedfiles/subscribe`, accepting `success=1`. Subscription replacement is deliberately excluded. The independent adapter uses only add-only requests and exposes status, never credentials, to Python. No upstream code/assets were copied or bundled.
- [Steamworks SubscribeItem](https://partner.steamgames.com/doc/api/isteamugc#SubscribeItem): subscriptions download/install as soon as possible. A web success response does not prove download completion. The native SDK is not bundled or initialized as Project Zomboid.
- The local Steam-owned `appworkshop_108600.acf` was inspected read-only. `WorkshopItemsInstalled` records per-item `manifest` and `timeupdated`. Readiness requires a nonzero installed manifest, matching detail manifest when present, a timestamp at least as current as fetched metadata, and an installed directory. The existing read-only scanner separately establishes Mod IDs. No manifest or mod contents are written by the app.
