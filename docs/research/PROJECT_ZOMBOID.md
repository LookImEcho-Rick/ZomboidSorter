# Project Zomboid mod-system research

This is the current evidence summary, refreshed through Milestone 18 on 2026-10-23. Build 42 is the primary target. The local Steam install was first inspected at 42.21.0; Steam is now on its official `legacy41` branch, which reports Build 41.78.21. The prior Build 42 directory was copied to a separate backup before that branch update. This is not a complete game-format specification. Sources distinguish developer material, community-maintained API references, local source, and unresolved behavior. Feature validation used disposable fixtures; no live save or server settings file was written.

## Load order and activation

The Indie Stone's announcement gives a version-folder selection rule but does not specify all content precedence, dependency syntax, or write targets. ZomboidSorter selects the highest numeric version folder not newer than the user's exact target build; it uses the common metadata candidate when no compatible versioned metadata file is available. Build 41 continues to use root metadata. The selected metadata drives details, dependency diagnostics, and sort proposals. File-overlap analysis still examines all candidates and does not infer runtime conflicts. This selection does not prove content compatibility or reproduce every loader rule. RimWorld sorting rules must not be transplanted.

The installed Build 42.21 `ModSelectorModel.lua` uses `getRequire()` and `getIncompatible()` for dependency state. `ModLoadOrderPanel:isCorrectOrder()` walks the selected list and rejects a mod when any declared required Mod ID has not appeared earlier. `ModLoadOrderPanel:autoSort()` first sorts Mod IDs alphabetically, then inserts required/load-after/load-before IDs using a separate algorithm. ZomboidSorter does not copy that UI algorithm; it builds a graph and proposes a deterministic topological order. A new fixture confirms that a required mod precedes its dependent under the same invariant checked by `isCorrectOrder()`. This source-level parity is not a runtime loader test.

PZMM reads `mods.txt` in saves and `mods/default.txt`, and its current source chooses the most recently modified save's file before falling back to the default list. It also has a separate `modmanager-mods.txt` integration. Treat PZMM behavior as an implementation lead rather than an authoritative contract. Vanilla Build 42.21 `ModSelectorModel:acceptChanges()` writes a selected save through `manipulateSavefile(saveFolder, "WriteModsDotTxt")`, while the global list uses `saveModsFile()`. The app's save adapter limits writes to one selected immediate `<Saves>/<mode>/<save>/mods.txt`, preserves existing maps, and creates an explicit version-1 list for a save that otherwise inherits global state. The app confirms before writes, backs up existing bytes, checks the snapshot before replacing, and verifies the result. All write validation uses temporary fixtures; no live save was modified.

The actual local `ModSelectorModel.lua` distinguishes the global `default` list from save/new-game `currentGame`. The global `Zomboid/mods/default.txt` and save `mods.txt` use the version-1 `mods`/`maps` shape. The app's global writer and separate save writer preserve their own target boundaries. The read-only save importer remains separate from the explicit save-apply action. The in-game preset file remains unsupported.

The read-only Workshop importer calls Steam's public `GetCollectionDetails` and `GetPublishedFileDetails` endpoints, filters collection items to PZ App ID `108600`, records missing/unavailable item IDs in app-owned profiles, and never subscribes or downloads. `GetPublishedFileDetails` also supplies a public Workshop item's full BBCode description. A direct lookup for an item already found in the local PZ Workshop folder may omit `consumer_appid`; preserve its description when that field is absent, and reject only an explicitly different app ID. [Steamworks ISteamRemoteStorage API](https://partner.steamgames.com/doc/webapi/ISteamRemoteStorage).

File-overlap analysis is opt-in and limited to files under each metadata candidate's `media/` folder. It hashes same-sized files within explicit limits and reports differing or unverified relative paths with both source paths. A path overlap does not establish that the game loads both candidates or that the runtime treats that resource as a replacement. Console diagnostics recognize only specific high-signal signatures (missing script definitions/fluids, a reported world-load stop, or Lua exceptions with explicit mod attribution). Generic `ERROR`, `WARN`, and `require(...) failed` messages are omitted because the local log contains benign engine and vanilla messages in those forms.

In the 2024 Build 42 transition announcement, The Indie Stone said it planned to disable mods on the first B42 load. That was a transition note, not a general rule to apply on every launch today.

## Existing tools assessed

- [PZMM](https://github.com/paraxaQQ/pzmm) is a native PyQt6 Windows desktop manager. Its code recursively scans local/Workshop trees, parses `mod.info`, associates Workshop IDs with contained Mod IDs, and recognizes multiple versioned metadata files. Useful for discovery cases and UI ideas; its version picker, deduplication, active-list precedence, and custom `modmanager-mods.txt` writes are implementation choices that need independent validation.
- [pz-mod-manager](https://github.com/WildBrianNL/pz-mod-manager) is a Pelican server-panel plugin, not a native Windows client. Its re-read-before-write approach for the server `.ini` is a useful safety pattern; server path and configuration logic are not the desktop target.

No REA or game binary analysis was used. Source and developer documentation were sufficient for a read-only discovery design. The unresolved runtime questions are recorded in `REA_FINDINGS.md` and should first be investigated through normal documentation/local game fixtures.

## Initial discovery contract (completed)

Implement only read-only Windows discovery and a basic PySide6 window:

1. Detect Steam libraries and the Project Zomboid install where possible; allow an explicit path if automatic detection fails.
2. Scan the user's local mod root and Steam Workshop app `108600` content root without subscribing, updating, copying, or writing.
3. Recognize B41 root metadata and B42 `common`/version-folder metadata. Preserve every candidate and the candidates from its physical entry directory. When the user supplies an exact build, select the highest compatible numeric folder and use its metadata consistently; do not infer a game version automatically.
4. Keep each Workshop item and each contained ModEntry distinct; preserve duplicate Mod IDs and report them rather than silently dropping one.
5. Parse `mod.info` defensively, retain source path and raw fields, and report missing/invalid metadata without crashing. Initial fields: name, ID, author, description, version, and declared requirements where syntax is verified.
6. Show discovered records, source, and diagnostics in the basic window. Include fixture coverage for the cases in the roadmap and identify fixture results as simulated; separately record whether a real local installation was checked.

This was the initial read-only scope. Later milestones added guarded global-list writes, profiles, dependency ordering, read-only public Workshop collection metadata, and opt-in diagnostics. Per-save writes, authentication, subscriptions, downloads, and mod deletion remain out of scope.

## Additional verification from the installed game (2026-10-22)

The local Steam installation and the user's global mod list were inspected read-only. No save directory was opened, and no game file was modified.

- The installed Lua source at `media/lua/client/OptionScreens/ModSelector/ModSelectorModel.lua` selects `ActiveMods.getById("default")` for the global Mod screen, and `"currentGame"` for a new game or selected save. The same file calls `saveModsFile()` after global changes, while a selected save uses `manipulateSavefile(saveFolder, "WriteModsDotTxt")`. `MainScreen.lua` copies the global default list when an old save has no mod list and resets `currentGame` separately. This supports a narrowly scoped global target; it does not authorize editing save-specific lists.
- The observed global file at `Zomboid/mods/default.txt` uses `VERSION = 1`, a `mods` block of ordered `mod = <ModID>,` lines, and a separate `maps` block. Its observed encoding was UTF-8 without BOM and CRLF, with 15 active IDs and no map entries. This is one real file sample; the parser accepts only the verified shape and preserves the map list. It refuses unknown versions/syntax rather than rewriting them.
- The game’s `ModSelectorModel.lua` reads `getRequire()` and `getIncompatible()` for dependency state. Its `ModLoadOrderPanel.lua` consumes `getLoadAfter()`, `getRequire()`, and `getLoadBefore()` when producing an automatic order. This is evidence that these constraints affect the official UI; do not claim a complete ordering contract until Milestone 5 compares cycle and tie behavior carefully.
- The game stores favorite/preset UI data separately in `pz_modlist_settings.cfg`. Build 42.20's [official feature overview](https://projectzomboid.com/blog/features-overview-build-42-20/) confirms the in-game manager supports searching, favorites, ordering, dependencies/incompatibilities, and shareable presets. This app complements that UI with richer library diagnostics and portable profiles.
- The local game reports Build 42.21.0. A read-only scanner run found 50 Workshop item folders, 57 logical mod entries, 80 `mod.info` candidates, and zero parser/duplicate diagnostics. The parser preserves repeated `description=` and `poster=` values.
- An opt-in read-only media scan indexed 17,120 files and found 2,732 potential differing/unverified path pairs. It shows 100 source-backed examples and makes no claim that every overlap is an in-game conflict; file-type behavior and candidate selection remain unresolved.
- The local `console.txt` parser read 2,398 lines and reported zero high-signal findings. Generic engine errors and vanilla `require` warnings are not promoted to mod faults.

## Build 41.78.21 Workshop scan (2026-10-23)

- Steam Properties showed `legacy41` / Build 41.78.21 selected; the appmanifest recorded `BetaKey = legacy41` after the update completed. The prior Build 42.21 install directory was copied outside the repository before changing branches.
- A read-only scan of the local mods and Workshop roots found 62 entries and 39 root-style Build 41 metadata candidates; the Build 41 overlap analyzer indexed 12,058 media files and reported 1,389 differing comparisons across 344 paths for all discovered mods. The current staged active list has 23 IDs, of which three resolve to root metadata candidates with no indexable media files, so that staged-only result does not establish the absence of conflicts.
- No game process was launched and no save, Workshop item, game configuration, or installed mod was written. This verifies the app against real local metadata and files, but not the game's runtime loader, active content precedence, or whether a reported path overlap causes an in-game conflict.

## Build 41/42 config-flow and scan measurements (2026-10-23)

- The local Steam install remains on `legacy41` and the preserved Build 42.21.0 install directory is available for read-only inspection. A scan of the real local mod and Workshop roots found 62 entries, 85 metadata files, and no scan diagnostics. Three scans took 0.070, 0.067, and 0.069 seconds (0.069-second median). The exact target resolver selected root-style Build 41 metadata for 39 entries and Build 42.21.0 metadata for 36 entries in that same library.
- Build 41 and Build 42.21.0 global-list flows were exercised against separate temporary `Zomboid/mods/default.txt` files. Each flow wrote ordered Mod IDs and maps, created a backup with the original bytes, and read back the updated values. No real global config or save was accessed, and no game was launched.
- Because the measured library scans complete below the 250 ms cache threshold, this machine does not reuse cached scan results. A slow scan result is eligible for reuse for 30 seconds when its roots have not changed; **Refresh** always runs a new scan. The real-library measurements therefore did not motivate caching for this machine's normal workload, but establish the behavior for larger libraries.
- These checks validate metadata selection and the app's guarded global-list file flow for both targets. They do not verify the game's runtime loader, content compatibility, save behavior, or gameplay.

## Sorting source check, build detection, and guarded game targets (2026-10-23)

- Build 42.21 `ModLoadOrderPanel:isCorrectOrder()` checks only the required-mod-before-dependent invariant; its `autoSort()` routine uses an alphabetical insertion approach with additional `loadModAfter` and `loadModBefore` handling. The app keeps its graph-based proposal. A fixture using `RequiredOnly` and `Core` confirms the required target appears first and the proposal includes that edge.
- An isolated Build 42.21 launch was attempted with a temporary cache/profile and test-only mod content. The process reached Lua initialization but then reported it could not find the game's `media/lua/shared/a_requires.lua`, even though that file exists in the backup tree. It stopped before the test mods reached their scripts or the main menu. Treat this as a failed runtime probe; sorting behavior is verified against the UI source and fixtures only. No live save or global configuration was changed.
- Build-family detection uses the Steam `legacy41` beta branch for Build 41 and the `VERSION_BUILD_42` marker in the installed `zombie/core/Core.class` (loose or in a game JAR) for Build 42. A bounded `Zomboid/version.txt` read supplies an exact version only when its timestamp is at least as new as Steam's `LastUpdated` manifest value and the detected family agrees. Otherwise, the user can select the family and enter an exact version manually. The detector does not guess from a Steam BuildID.
- Build 42.21 `ServerSettingsScreen.lua` joins the `Mods` Mod ID list and `WorkshopItems` numeric list with semicolons and writes the corresponding `ServerOptions` keys independently. The new server adapter preserves every other line in a selected `<Zomboid>/Server/<name>.ini`, including `Map`; it rejects duplicate/missing keys, malformed lists, linked targets, stale snapshots, and non-server paths.
- Fixture checks cover save-list writes to existing and inherited saves, map/BOM/CRLF preservation, timestamp backups, stale-file rejection, exclusive creation, server-list parsing/writes and preservation, and the app's explicit save/server actions. No real save or server `.ini` was written. The local save format was previously inspected read-only, which is one sample rather than broad build coverage.
The current configuration field and profile manager write only the global default list after explicit confirmation. The retired **Apply Elsewhere** action could target one immediate save `mods.txt` or a server `.ini`; it did not write `Sandbox Presets` or `ActiveMods` directories. The retired save importer read only immediate `<mode>/<save>/mods.txt` files and treated a missing file as inheritance without substituting or changing the global list. These adapters and import paths were removed during the global-only scope cleanup (see roadmap milestones 13, 16, 17, and 20); this paragraph preserves historical format research and does not describe current app support. App-owned Mod Packs retain Mod IDs, uniquely matched Workshop IDs, and optional ordered maps. Fixture tests from the retired implementation covered existing and inherited save targets, malformed data, file preservation, and stale snapshots. One local save list was inspected read-only and had the version-1 shape with 11 Mod IDs and no map entries; that remains one sample, not build-wide format verification. No live save file was changed.
