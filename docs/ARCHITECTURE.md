# Architecture decisions

## Technology

- **Python 3.14+ and PySide6/Qt 6.** RimSort already uses this UI stack and layered Python structure; it gives a native desktop UI and avoids introducing a second implementation language. The `pyproject.toml` sets the dependency boundary.
- **Windows first, portable core.** Use `pathlib` and isolated platform path discovery so filesystem parsing and domain logic remain portable. Keep Windows/Steam detection behind a service.
- **No runtime database for the first milestone.** Available Mods can operate on filesystem paths and in-memory records. Add persistence only when a milestone needs it.

The project's original code uses GPL-3.0-or-later. PySide6 has LGPLv3/GPLv3 and commercial licensing options; the exact Qt/WebEngine redistribution materials remain a binary release gate. RimSort is GPL-3.0: we are reusing its documented ideas and independently implementing behavior, not copying its source. If source code is later copied or adapted, revisit the source attribution and license compatibility before distribution.

## Boundaries

- **Domain:** `WorkshopItem` (numeric Workshop identity and installation path) contains zero or more **ModEntry** records (one per logical Mod ID at an entry path, with its own metadata candidates and source). Retain all candidates from the physical entry directory so version-specific Mod ID changes can be resolved without treating old and new IDs as simultaneously active.
- **Available Mods:** read-only path detection, directory traversal, and metadata parsing. A scanner returns records and diagnostics; it never writes to the game.
- **Game I/O:** `gameio/active_mods.py` reads and writes only the verified global `Zomboid/mods/default.txt` version-1 shape. Apply runs a library/dependency preflight, previews changes, uses a default-No confirmation, checks for links and concurrent changes, backs up existing bytes, writes atomically, and verifies the result. Restore accepts only validated timestamped sibling backups, rechecks the current snapshot, backs up the current file, writes atomically, and verifies the restored bytes. The adapter rejects unsafe targets and unknown data rather than guessing; save and server configuration files are outside the product scope.
- **Application/UI:** thin PySide6 views call services and display state. Global apply confirmations show bounded ordered-list changes for Mod IDs and maps. The preflight checks missing/duplicate active IDs and declared dependency findings against the latest scan; findings are advisory and shown in full by `ui/preflight_dialog.py` in a scrollable, copyable review with Cancel as the default before an explicit continue choice. Dependency messages name the declaring Mod ID and show the selected metadata file once in diagnostics and preflight. Available Mods metadata warnings stay on Available Mods rows and its heading; Active Order rows report missing or ambiguous active Mod IDs, with dependency findings summarized below that list. The Available Mods build filter controls which metadata layouts appear, while compatibility warnings follow the selected target metadata independently of that filter. Rebuilding equivalent lists preserves each list's scroll position, current row, selection, search, and staged order where those records remain available; the last inspected Mod ID stays in Details, and explicit staging actions keep that Mod ID visible when it moves lists. The global target has its apply, launch, and restore actions in Mod Workspace and Paths & Settings. Restore uses a newest-first preview dialog before its separate default-No confirmation. `configuration.py` owns the global active-list load, target/path checks, stale-snapshot checks, and apply workflow; the UI owns prompts and presentation, while `gameio/active_mods.py` owns the file format and protected disk writes. Keep filesystem and parsing logic outside widgets. Present warnings as evidence-backed diagnostics.
- **Profiles:** app-owned JSON profiles (shown as Mod Packs in the UI) live under the platform config directory in a standard install, or under the application folder's `data/` directory when the portable marker is present. Schema v4 adds exact shared collection-content references; profiles without references retain v2/v3 serialization. Older v1/v2/v3 packs remain valid. Ordered Mod IDs, Workshop IDs, and optional explicit maps retain their previous meaning. Before **Apply**, the pack manager previews the ordered profile and its bounded Mod ID/map changes against the loaded global list. Applying a pack asks before replacing unfinished manual staging and restores that staging if the later preflight or write is cancelled or fails. Applying an explicit map list asks before changing the global maps; profiles without maps preserve the currently loaded list. Writes use the verified global list, backup, atomic replacement, and validation safeguards. Manual list edits remain staged until the user applies them.
- **Dependencies/sorting:** parse declared constraints from each `mod.info` candidate. For a user-selected exact game build, use only that build's resolved metadata candidate; without an exact target, apply an edge only when candidate declarations agree. Explicit user before/after rules are stored in app settings and combined with metadata constraints for proposals. The orderer returns a deterministic proposal, uses the current list as its tie-breaker, and refuses to force a cyclic result. A fixture checks that required mods precede dependents as Build 42.21's UI validator expects; runtime loader equivalence remains unverified.
- **Workshop/collections:** `workshop_catalog.py` reads Steam's bounded public catalog for native search/sort/tag/pagination. `workshop.py` owns public collection expansion and item metadata. `steamcmd.py` obtains Valve's signed helper, verifies Authenticode, isolates its self-updater process tree, reuses receipt-current downloads, batches new anonymous downloads in groups of up to 200, and checks each success marker against Steam installation receipts. After SteamCMD stops with partial results, verified completed items enter the shared cache before an error is reported. `collection_store.py` hashes relative paths, entry types, and file bytes into shared immutable content objects while avoiding a duplicate source hash during verified copy. Schema-v4 profiles retain exact Workshop-ID/content-hash references; v1–v3 remain supported. The collection review distinguishes ordinary local installation from private downloads and content referenced by a saved collection pack, and default names avoid collisions with existing packs. Only loading a pack invokes `collection_deployment.py`: prepare and verify app-owned local copies off the UI thread, reject nonidentical installed-ID conflicts, archive the previous recorded copies on the same volume, rescan, then apply through the existing guarded global writer. Cancelled/failed writes restore the prior deployment and staged view; uncertain persisted writes retain matching files and require inspection. User/Steam folders are never overwritten or moved. Cached objects are excluded from normal scans; active game-ready copies make disabled pack mods available for re-adding. Imports do not change subscriptions or game files. Recovery copies consume extra disk and are retained. `ui/collection_load_dialog.py` owns cancellable preparation/recovery UI. See `docs/research/WORKSHOP_COLLECTION_IMPORT.md`.
- **Advanced diagnostics:** overlap checks walk only candidate `media/` trees, skip symlinks, cap file/pair/hash work, and compare shared relative paths. Results group comparisons by shared path, summarize different versus unverified content, and expose bounded source examples with path/Mod ID search and status filters. Console parsing is opt-in, size-limited, and recognizes only specific high-signal signatures. Both return evidence rather than inferred runtime causality.
- **UI/persistence:** PySide6 views call service modules; scans and expensive diagnostics run in `QThread`. `ui/main_window.py` composes focused modules for layout, library, staging, profiles, global configuration, discovery, diagnostics, details, updates, support reporting, and lifecycle. The main layout composes separate workspace and Workshop collection tab builders in `ui/window_workspace_layout.py` and `ui/window_workshop_layout.py`. Reusable workers and list/preview widgets live in `ui/window_workers.py` and `ui/window_widgets.py`. `support_report.py` emits aggregate path and scan health without path values, mod identifiers, logs, or file contents; the UI previews the report before the user saves it. `QSettings` stores window geometry and selected paths in the registry for a standard install and in `data/settings.ini` for portable mode. The embedded Workshop defers Qt WebEngine imports until its browser is created, warms its first page after the window appears and the library scan finishes, and freezes the hidden page when Chromium recommends a lower-resource state. After the user has visited the tab, hidden pages are discarded after 2 seconds even when the site keeps Chromium's recommendation at Active; this releases the renderer but may interrupt page audio or unsent forms. Returning reloads the current URL while the named WebEngine profile retains Steam session cookies under app data for standard installs and under `data/workshop-browser/` for portable mode. On startup, initial and restored window geometry is kept inside the selected screen's available bounds when that screen can fit the configured minimum size. The installer remembers the data mode and warns before an interactive switch; it never moves app data automatically. Profiles are stored separately from game data.
- **Packaging:** PyInstaller produces a Windows onedir app, and Inno Setup wraps its complete output folder in a per-user installer. The installer has standard and portable data modes plus optional shortcuts. Standard app-owned profiles/settings stay outside the install directory. Releases are unsigned; the README explains the expected SmartScreen warning and how to verify the official download. The release workflow creates a GitHub artifact attestation for the installer and checksum, which users can verify with GitHub CLI. A clean-machine pass and Qt/WebEngine redistribution review remain binary release gates.

## Initial source layout

`src/zomboid_mod_manager/` is the package root. Keep the existing `discovery/`, `gameio/`, `diagnostics/`, `sorting/`, and `ui/` modules focused, with realistic fixtures under `tests/`. `configuration.py` contains the application workflow for the global active-mod list. The embedded Steam Workshop tab is isolated in `ui/workshop_browser.py`; it owns its controls, navigation, deferred WebEngine imports, post-scan warm-up, themed loading surface, and hidden-page lifecycle. Avoid adding abstraction layers before a concrete milestone requires them.

The discovery records preserve source path/type, Workshop item ID when available, Mod ID, every observed version candidate, raw metadata, and parse warnings. The app detects Build 41 from Steam's selected legacy branch and Build 42 from its installed Core class marker. It uses the exact version from `Zomboid/version.txt` only when the file is at least as recent as Steam's install update; otherwise the version field remains available for manual entry. An exact Build 42 candidate selection does not establish content compatibility. A Workshop item is not a mod entry: one item can provide several Mod IDs.

## Persistent individual Workshop installs

The native collection catalog/parser and browser also support the `readytouseitems` catalog (`file_type=0`), displaying current `subscriptions` alongside author/favorites/update metadata. The Available Mods **Browse Mods…** action reuses these components and the cancellable progress worker. `local_install.py` owns individual installation: verify public PZ metadata, download via the existing anonymous SteamCMD adapter, scan actual Mod IDs, reject installed-ID conflicts, prepare and hash complete entry folders outside discovery, and rename without overwriting. Cancellation/commit failure moves newly installed copies back into preparation. Existing copies are never replaced; exact repeats are idempotent. These `WorkshopLocal_<item>_<entry>` local folders are never recorded in collection ownership, so collection switches cannot archive them. The global writer is not involved. A successful install refreshes the normal scanner while retaining the staged active list.
