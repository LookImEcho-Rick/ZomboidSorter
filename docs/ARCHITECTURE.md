# Architecture decisions

## Technology

- **Python 3.14+ and PySide6/Qt 6.** RimSort already uses this UI stack and layered Python structure; it gives a native desktop UI and avoids introducing a second implementation language. The `pyproject.toml` sets the dependency boundary.
- **Windows first, portable core.** Use `pathlib` and isolated platform path discovery so filesystem parsing and domain logic remain portable. Keep Windows/Steam detection behind a service.
- **No runtime database for the first milestone.** Discovery can operate on filesystem paths and in-memory records. Add persistence only when a milestone needs it.

The project's original code uses GPL-3.0-or-later. PySide6 has LGPLv3/GPLv3 and commercial licensing options; the exact Qt/WebEngine redistribution materials remain a binary release gate. RimSort is GPL-3.0: we are reusing its documented ideas and independently implementing behavior, not copying its source. If source code is later copied or adapted, revisit the source attribution and license compatibility before distribution.

## Boundaries

- **Domain:** `WorkshopItem` (numeric Workshop identity and installation path) contains zero or more **ModEntry** records (one per logical Mod ID at an entry path, with its own metadata candidates and source). Retain all candidates from the physical entry directory so version-specific Mod ID changes can be resolved without treating old and new IDs as simultaneously active.
- **Discovery:** read-only path detection, directory traversal, and metadata parsing. A scanner returns records and diagnostics; it never writes to the game.
- **Game I/O:** keep Build 41, Build 42, client/save, and server configuration surfaces separate. `gameio/active_mods.py` writes only the verified global `Zomboid/mods/default.txt` version-1 shape; it refuses unknown syntax, save paths, symlink targets, duplicate identifiers, and concurrent changes. It backs up before an atomic replacement and validates the result. `gameio/save_mods.py` reads only immediate save `mods.txt` files under the selected Saves folder and never edits save data. Save-specific writes and server config adapters are not implemented.
- **Application/UI:** thin PySide6 views call services and display state. `configuration.py` owns the global active-list load, target/path checks, stale-snapshot checks, and apply workflow; the UI owns prompts and presentation, while `gameio/active_mods.py` owns the file format and protected disk writes. Keep filesystem and parsing logic outside widgets. Present warnings as evidence-backed diagnostics.
- **Profiles:** app-owned JSON profiles (shown as Mod Packs in the UI) live under the platform config directory in a standard install, or under the application folder's `data/` directory when the portable marker is present. Schema v3 stores ordered Mod IDs, Workshop IDs, and an optional explicit ordered map list; v1/v2 profiles remain valid and mean that no map list was saved. **Apply** from the pack manager is an explicit action that writes selected IDs to the verified global list using its backup, atomic replacement, and validation safeguards. Applying an explicit map list asks before changing the global maps; profiles without maps preserve the currently loaded list. Save-list import copies both ordered Mod IDs and maps into a profile. Manual list edits remain staged until the user applies them.
- **Dependencies/sorting:** parse declared constraints from each `mod.info` candidate. For a user-selected exact game build, use only that build's resolved metadata candidate; without an exact target, apply an edge only when candidate declarations agree. Explicit user before/after rules are stored in app settings and combined with metadata constraints for proposals. The orderer returns a deterministic proposal, uses the current list as its tie-breaker, and refuses to force a cyclic result; it does not claim full Java loader equivalence.
- **Workshop:** use public read-only Steam Remote Storage endpoints for collection and item metadata. Collection profiles retain both Mod IDs and numeric Workshop IDs. No login, subscription, download, or update action is performed.
- **Advanced diagnostics:** overlap checks walk only candidate `media/` trees, skip symlinks, cap file/pair/hash work, and compare shared relative paths. Results group comparisons by shared path, summarize different versus unverified content, and expose bounded source examples with path/Mod ID search and status filters. Console parsing is opt-in, size-limited, and recognizes only specific high-signal signatures. Both return evidence rather than inferred runtime causality.
- **UI/persistence:** PySide6 views call service modules; scans and expensive diagnostics run in `QThread`. `ui/main_window.py` composes focused modules for layout, library, staging, profiles, configuration, discovery, diagnostics, details, updates, and lifecycle. Reusable workers and list/preview widgets live in `ui/window_workers.py` and `ui/window_widgets.py`. `QSettings` stores window geometry and selected paths in the registry for a standard install and in `data/settings.ini` for portable mode. The installer remembers the data mode and warns before an interactive switch; it never moves app data automatically. Profiles are stored separately from game data.
- **Packaging:** PyInstaller produces a Windows onedir app, and Inno Setup wraps its complete output folder in a per-user installer. The installer has standard and portable data modes plus optional shortcuts. Standard app-owned profiles/settings stay outside the install directory. Releases are unsigned; the README explains the expected SmartScreen warning and how to verify the official download. The release workflow creates a GitHub artifact attestation for the installer and checksum, which users can verify with GitHub CLI. A clean-machine pass and Qt/WebEngine redistribution review remain binary release gates.

## Initial source layout

`src/zomboid_mod_manager/` is the package root. Keep the existing `discovery/`, `gameio/`, `diagnostics/`, `sorting/`, and `ui/` modules focused, with realistic fixtures under `tests/`. `configuration.py` contains the application workflow for the global active-mod list. The embedded Steam Workshop tab is isolated in `ui/workshop_browser.py`; it owns its controls, navigation, and lazy WebEngine view. Avoid adding abstraction layers before a concrete milestone requires them.

The discovery records preserve source path/type, Workshop item ID when available, Mod ID, every observed version candidate, raw metadata, and parse warnings. An exact Build 42 candidate is selected only after the user enters the game version; the game build is not auto-detected, and selection does not establish content compatibility. A Workshop item is not a mod entry: one item can provide several Mod IDs.
